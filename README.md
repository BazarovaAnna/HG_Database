# HG Database — скрипты таблицы персонажей

Код Apps Script для Google-таблицы «HG Character Database»: учёт персонажей Pathfinder 1e — регистрация, повышения уровня, партии, инвентарь и золото, проверка по правилам.

Скрипты не хранят данные сами: они читают одни листы таблицы и пишут в другие. Всё, что ниже называется «лист», — вкладка этой таблицы.

Что делать мастеру руками — после каждой формы, при новом классе, расе или правке формы — в [памятке мастеру](GM_GUIDE.md).

## Синхронизация с Google

Проект выгружен и отправляется через [clasp](https://github.com/google/clasp). Источник правды — этот репозиторий, но редактор Apps Script тоже позволяет менять код, поэтому порядок такой:

1. `clasp pull` и `git status` — убедиться, что в Google ничего не меняли мимо git. Если `git diff` не пустой, сначала разобраться с этим.
2. Правка в ветке, коммит.
3. `clasp push` — перезаписывает проект в Google **целиком** локальной версией.
4. `clasp pull` ещё раз: `git status` должен остаться чистым.

`clasp push` отправляет только `.js`, `.gs`, `.html` и `.json` (см. `.clasp.json`); README и `.gitattributes` в Google не попадают. `.gitattributes` закрепляет LF — без него `core.autocrlf` на Windows превратит файлы в CRLF, и первый же push изменит каждую строку проекта.

В Apps Script у всех файлов **общая область видимости**. Две функции с одним именем в разных файлах не дают ошибки — молча работает та, что загружена последней. Имена функций должны быть уникальны по всему проекту.

## Как устроены данные

```
 LvlUP ──── processLevelUps ────► Registration  (правит ячейки)  + LevelUp Log (журнал для отката)

 Registration ── FILTER, формулы ──► Database ──► Refresh …                 ──► Feats, Skills, Spells
                                        │     └─► Find data Discrepancies  ──► Discrepancies
                                        │
 Games ─── опыт, формулой ──────────────┘  (current_gold — формулой из Transactions)

 Database.starting_gold ─┐
 Games                   ├── Process … ──► Transactions ── Rebuild Inventory Sheet ──► Inventory
 Inventory(raw)          ┘
```

- `Reference tables` — справочник: расы, классы, прогрессии БМА и спасбросков, боги, навыки, опыт.
- `Masters` — мастера, заполняется вручную: `vks` (ссылка ВК) и `master` (имя, как оно будет в форме партий).
- `Inspector` — карточка выбранного персонажа: только формулы поверх `Database`, `Skills`, `Feats`, `Spells`, `Inventory`.
- `Column matchups` — какой колонке формы соответствует какое поле (см. ниже).

Главное, что нужно держать в голове:

- **`Registration` — источник правды о персонаже.** Это лист ответов формы регистрации, и `processLevelUps` правит его ячейки напрямую. `Database` собирает из него одобренные заявки (колонка `Approved?`) формулами `FILTER` и досчитывает всё остальное: модификаторы, КБ, спасброски, пункты навыков.
- **Характеристики в `Registration` — базовые значения**, без расы и повышений за уровни. Итог считает `Database`: база + расовая прибавка из справочника (`*_add`) + ручная поправка для вариантов расы (`*_racial_var`) + число повышений из колонок «Which ability did you increase at [Level N]» (`*_ability_increase`). Поэтому скрипты сырое значение не трогают.
- **Строка 4 листа `Database` — ключи полей** (`char`, `skills`, `str_mod`, `cast_class` …), данные начинаются со строки 5. Скрипты ищут колонки `Database` по этим ключам, а не по буквам, поэтому колонки можно переставлять. Переименовать ключ — значит сломать скрипт, который его читает.
- **`Transactions` — журнал движения предметов и золота.** Строки только добавляются. Текущее золото (`current_gold` в `Database`) — сумма строк `gold` по персонажу; лист `Inventory` — свёртка журнала.
- **Опыт скрипты не считают.** `Database` суммирует опыт формулой прямо из листа `Games`: имя персонажа ищется в списке участников как отдельный элемент (`,Имя,` в `,Имя1,Имя2,` без пробелов, без учёта регистра). Поиск простой подстроки здесь не годится — «Ар» засчитал бы себе партии «Арлин» и «Варвары».

## Меню PF1e Tools

Меню создаёт `onOpen` в `Main.js` при открытии таблицы.

| Пункт | Функция | Файл |
|---|---|---|
| Refresh ALL normalized tables | `parseAll` → `parseFeats`, `parseSkills`, `parseSpells` | `Main.js` |
| Refresh Feats / Skills / Spells only | `parseFeats` / `parseSkills` / `parseSpells` | `* Normalizer.js` |
| Process Level-Ups | `processLevelUps` | `Lvlup Processor.js` |
| Process ALL Transactions | `processTAll` → `initializeStartingGold`, `processGameSessions`, `processInventory` | `Main.js` |
| Process Starting Gold → Transactions | `initializeStartingGold` | `Transaction Processor.js` |
| Process Game Sessions → Transactions | `processGameSessions` | `Transaction Processor.js` |
| Process Inventory Form → Transactions | `processInventory` | `Transaction Processor.js` |
| Rebuild Inventory Sheet | `rebuildInventory` | `Transaction Processor.js` |
| Find data Discrepancies | `findDiscrepancies` | `Discrepancy Finder.js` |
| Sync form choices | `syncFormChoices` | `Form Rules.js` |
| Apply form validation | `applyFormValidation` | `Form Rules.js` |

**Process ALL Transactions не пересобирает `Inventory`.** После него нужен отдельный запуск *Rebuild Inventory Sheet*, иначе лист `Inventory` (и блок инвентаря в инспекторе) покажет состояние до обработки. Золото в карточке обновится сразу — оно считается формулой из `Transactions`.

## Модули

### Нормализаторы: `Feats Normalizer.js`, `Skills Normalizer.js`, `Spells Normalizer.js`

Раскладывают текстовые поля `Database` («через запятую») в плоские таблицы — по строке на черту, навык или заклинание. Каждый запуск **полностью пересоздаёт** свой лист.

Ручные пометки мастера переживают пересборку: перед очисткой скрипт запоминает их и возвращает в строки с тем же ключом.

| Лист | Откуда | Что сохраняется при пересборке | Ключ сохранения |
|---|---|---|---|
| `Feats` | `feats`, `class_features`, `special_abilities` | `gm_notes` | персонаж + тип + название |
| `Skills` | `skills` | `misc_mod` (если не 0) | персонаж + навык |
| `Spells` | `cant`, `spell1` … `spell9` и `*_num` | `gm_notes` | персонаж + уровень заклинания + название |

Если запись переименовать (исправить опечатку в названии черты), ключ изменится и пометка к ней пропадёт.

**Feats.** Тип строки — `feat`, `class feature` или `special ability`, по исходному полю. Метка в квадратных скобках уходит в колонку `source`: `Stern Gaze [class]` → название `Stern Gaze`, источник `class`.

**Skills.** Формат поля: `название ранги, название ранги` — последнее слово записи, если это число, считается рангами. Для каждого навыка:
- характеристика и классовость берутся из таблицы SKILLS в `Reference tables`. Название ищется сначала точно, потом по началу строки, потом по вхождению — поэтому `perform (dance)` находит `Perform`;
- навык классовый, если любой из классов персонажа перечислен в колонке `Class Skill` справочника (через запятую, без учёта регистра);
- `ability_score` — это **модификатор** характеристики (`str_mod` и т. д.), а не значение;
- `class_mod` = 3, если навык классовый и рангов больше нуля;
- `sum` — формула `=F+G+H+I`.

Дубли в исходной строке не схлопываются: навык, записанный дважды, даст две строки.

**Spells.** Персонажи с `is_caster` пустым, `no` или `нет` пропускаются. `*_num` имеет формат `известно/в день` — Spells Known / Spells per Day с листа персонажа, в день — вместе с бонусными заклинаниями (разделитель `/` или `;`); прочерк означает «без ограничения» и выводится как `∞`. Колонки листа `Spells` по исторической причине называются `known` и `prepared`.

Нормализатор черт берёт имена листов и ключи из `CONFIG` в `Main.js`; навыки и заклинания — из констант в своих файлах (`'Database'`, строка 4).

### `Lvlup Processor.js` — повышения уровня

Переносит одобренные ответы формы `LvlUP` в строку персонажа в `Registration` и записывает каждое изменённое поле в `LevelUp Log` (старое значение → новое). Работает в две фазы.

**Фаза 1 — откат.** Повышение считается обработанным, если в журнале есть строки с его отметкой времени и именем персонажа. Если у обработанного повышения сняли галочку `Approved?`:
- откатываются **все** обработанные повышения этого персонажа с уровнем не ниже снятого — от старшего к младшему. Снять одобрение с 4-го уровня — значит откатить 4-й, 5-й, 6-й;
- у каскадно откаченных уровней галочка снимается автоматически, и это видно в итоговом сообщении;
- поле возвращается к старому значению, **только если сейчас в нём ровно то, что записал скрипт**. Если мастер успел поправить ячейку руками, она не трогается и считается в «Skipped fields»;
- строки журнала для откаченного повышения удаляются.

**Фаза 2 — применение.** Для каждого одобренного и ещё не обработанного повышения:

| Что в форме | Что происходит в `Registration` |
|---|---|
| Новый уровень | `inputLvl` заменяется |
| Класс | уровень класса +1; если такого класса нет — записывается в первый пустой слот (до трёх), с уровнем 1 и архетипом |
| Выпавшие хиты | прибавляются к `hpTotal` |
| Бонус любимого класса (`HP` / `Skill` / `Racial`) | соответствующий счётчик +1 |
| Повышение характеристики | на уровнях 4/8/12/16/20 — записывается в колонку `abilityInc<уровень>`; сырое значение **не меняется**, повышения прибавляет `Database` (`*_ability_increase`). На другом уровне — не записывается, в журнал идёт `IGNORED` |
| Новый любимый класс | заменяется |
| Черты, особенности, способности, штрихи, недостатки | дописываются через запятую |
| Ранги навыков | сливаются: ранги одноимённого навыка складываются, новые навыки добавляются; запись без числа = +1 ранг |
| Заклинатель? | заменяется |
| Число чар / заклинаний | `*_num` заменяется, списки дописываются |
| Переобучение | `Старое -> Новое` (или `-Старое` и `Новое` на двух строках) — замена в первом списке, где найдено старое; не найдено — пишется в журнал как `NOT FOUND` |

Персонаж в `Registration` ищется по имени — берётся **первая** строка с таким именем.

### `Transaction Processor.js` — золото и предметы

Пишет в `Transactions` строки вида `timestamp | source | character | item_name | quantity | cost | weight | notes`. Строки только добавляются, отката нет.

**Повторная обработка не происходит**: источник считается обработанным, если в `Transactions` уже есть строка с его отметкой времени (`game` — по отметке, `inventory` — по отметке и персонажу). Следствия:
- исправить уже обработанный ответ формы недостаточно — изменения не попадут в журнал; поправить нужно сам `Transactions`;
- снятие `Approved?` с обработанного ответа ничего не откатывает.

**Стартовое золото** (`initializeStartingGold`): для каждого персонажа из `Database`, у которого в журнале ещё нет ни одной строки `gold`, добавляет `starting_gold`.

**Партии** (`processGameSessions`, лист `Games`; колонки одобрения нет — обрабатываются все строки):
- награда золотом — каждому из перечисленных через запятую участников;
- «Other gold changes»: `Имя: -10; Имя: +13`;
- «Additional rewards»: `Имя: предмет кол-во цена вес, предмет; Имя: -предмет` — минус перед предметом означает изъятие.

**Форма инвентаря** (`processInventory`, лист `Inventory(raw)`, только с `Approved?`):

| Поле | Предмет | Золото |
|---|---|---|
| Items bought | `+кол-во` по указанной цене | `−цена × кол-во` |
| Items sold | `−кол-во` | `+⌊цена × кол-во / 2⌋`, цена — из прошлых записей журнала |
| Items gifted | `−кол-во` | — |
| Items got | `+кол-во` | — |
| Other gold changes | — | `±сумма` |

Проданный или подаренный предмет, которого нет у персонажа, всё равно списывается, но с ценой `N/A`, и попадает в предупреждения.

**Формат предмета.** Числа снимаются **с конца** записи: `Название [кол-во] [цена] [вес]`. `Potion of Cure Light Wounds 1 50` — одна штука по 50. Для продажи и дарения — только `Название [кол-во]`. Если в названии предмета есть число, оно будет принято за количество.

**`Inventory`** (`rebuildInventory`) — пересобирается из журнала с нуля: количество суммируется по персонажу и предмету, цена и вес берутся из последней ненулевой записи, предметы с количеством ≤ 0 скрываются (кроме `gold`). Колонка `notes` при пересборке **не сохраняется**.

### `Discrepancy Finder.js` — проверка по правилам

Проходит по всем персонажам `Database` и пересоздаёт лист `Discrepancies`. Три уровня: ❌ ERROR — нарушение правил, ⚠️ WARNING — нужно посмотреть мастеру, ℹ️ MINOR — мягкое правило.

| # | Проверка | Уровень |
|---|---|---|
| 1 | Уровень из формы ≠ сумме уровней классов | ERROR |
| 2 | Мировоззрение дальше чем на шаг от бога | MINOR |
| 3 | Паладин не LG, монах не законный, варвар законный | ERROR |
| 4 | Любимый класс не из классов персонажа (несколько — через `/` или запятую) | ERROR |
| 5 | Класса нет в справочнике — проверки БМА и спасбросков пропускаются | ERROR |
| 6 | Сумма бонусов любимого класса ≠ уровню в любимых классах | WARNING |
| 7 | Сырая характеристика больше 20 | WARNING |
| 8 | Указан вариант расы, но `*_racial_var` пустые (0 допустим) | WARNING |
| 9 | Хиты вне диапазона мин–макс; ровно максимум (MINOR) или минимум (WARNING) при уровне > 1 | ERROR / MINOR / WARNING |
| 10 | БМА ≠ сумме по классам из справочника | ERROR |
| 11 | Базовые спасброски ≠ сумме по классам | ERROR |
| 12 | Черт меньше минимума или больше минимума + 3 | WARNING |
| 13 | Нет классовых особенностей с 3-го уровня; мало особенностей с 4-го | WARNING / MINOR |
| 14 | Пункты навыков — см. ниже | ERROR / WARNING |
| 15 | `is_caster` не совпадает с колонкой `Caster?` справочника | WARNING |
| 16 | Число заклинаний в списке ≠ известным или подготовленным; число есть, а список пуст | WARNING |

**Пункты навыков (14).** Перерасход до `2 × уровень` пунктов — WARNING, больше — ERROR. Запас в два пункта за уровень — это опциональное правило фоновых навыков (background skills): оно включено не у всех персонажей, поэтому такой перерасход не ошибка, а сигнал мастеру проверить. Недорасход — тоже WARNING.

Минимум черт (12): `⌊(уровень + 1) / 2⌋`, +1 человеку, плюс бонусные черты классов по таблице `CLASS_BONUS_FEAT_MILESTONES` в начале файла (воин, монах, следопыт, волшебник, бладрейджер).

Справочник читается по заголовкам: таблица классов — строка, где есть `Class` и `BAB`; прогрессии — строка с `Level` и `Full BAB` / `Good Save`; боги — `Deity` и `Alignment`. Названия колонок менять нельзя, порядок — можно.

### `Form Rules.js` — ограничения в формах

Скрипты и формулы разбирают ответы форм как текст, поэтому формат ввода важен: запятая внутри скобок разобьёт черту на две, `0,1` в списке предметов — запись на две, опечатка в названии класса при повышении заведёт персонажу новый класс. Этот модуль не даёт ввести такое в саму форму.

Формы находятся через листы ответов (`sheet.getFormUrl()`), адреса в коде не хранятся. Запускающему нужны права редактора на все четыре формы.

- **`applyFormValidation`** ставит проверку ответа («регулярное выражение — соответствует») на вопросы со свободным вводом. Шаблоны и тексты подсказок — в `RX` и `HELP`, какой вопрос что принимает — в `FORM_RULES`. Шаблоны в синтаксисе RE2 (движок Google): без lookahead и обратных ссылок.
- **`syncFormChoices`** заполняет варианты выбора из таблицы: имена персонажей из `Database` — в LvlUP, Inventory, Games; классы, расы и боги — из `Reference tables`; мастеров — из колонки `master` листа `Masters` в вопрос «Master» формы Games. Пустой источник вариантов не стирает: вопрос остаётся как был, а в отчёте появляется ошибка. «Favored class» и «New Favorite Class» — флажки с классами из справочника (несколько любимых классов Google запишет через запятую); если вопрос ещё текстовый, вместо вариантов ставится шаблон из того же списка (несколько — через `/`). Запускать после одобрения новой заявки и после правки справочника.

Вопросы ищутся по названию. Не найденный или не того типа вопрос попадает в отчёт и пропускается — **скрипт никогда не создаёт и не пересоздаёт вопросы**: новый вопрос пишет ответы в новую колонку в конце листа, и это ломает `Column matchups` и формулы `Database`. Тип вопроса (текст → список) меняется только в редакторе формы — так вопрос и его колонка ответов сохраняются.

Десятичный разделитель: в одиночных числовых полях допустимы и `42,37`, и `42.37` — ответ разбирает таблица в своей локали. Внутри списков (предметы, «Имя: сумма») — только точка: там текст разбирает скрипт, а запятая разделяет записи.

## Лист `Column matchups`

Формы Google кладут ответы в колонки по порядку вопросов. Чтобы скрипты не ломались при правке формы, номера колонок вынесены на этот лист: четыре блока по три колонки — `Registration` (A–C), `LvlUP` (E–G), `Inventory(raw)` (I–K), `Games` (M–O). В каждом: имя поля, **номер колонки** (с единицы), текст вопроса для справки. Скрипт читает только первые две колонки блока, начиная с третьей строки; положение блоков зашито в `loadColumnMappings`.

Добавили вопрос в форму — проверьте номера в соответствующем блоке. Поле с пустым или нулевым номером скрипт считает отсутствующим и молча пропускает.

Для заклинаний 2–9 уровня номера колонок вычисляются от `spell1Num` / `spell1` (и `newSpell1Num` / `newSpell1` для `LvlUP`) с шагом 2 — пары «число, список» в формах должны идти подряд.
